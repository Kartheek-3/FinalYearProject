# Planning Execution Section — Semantic Fix Report

## Root Cause

The `PlanningSectionExecution` section failed validation 3 times because `qwen2.5-coder` placed technology stack names into `ImplementationTask.requirement_ids` and `ImplementationTask.acceptance_criteria`.

**Exact confusing values**:
```
'React', 'TypeScript', 'FastAPI', 'Python', 'SQLite', 'Docker'
```

These are technology names from the project stack. They do NOT conform to the `Identifier` regex (`^[a-z][a-z0-9_]{1,63}$`) and have no meaning as requirement or acceptance criteria identifiers.

**The model's semantic confusion**: The prompt context includes the technology stack. The model was mapping "which technologies does this task use?" (a reasonable question) to `requirement_ids` and `acceptance_criteria`, conflating technologies with requirements.

---

## Distinction: Technologies vs Requirement Identifiers

| Concept | Example | Allowed in requirement_ids? |
|---|---|---|
| Technology name | `React`, `FastAPI`, `SQLite` | **NO** — tech names, not IDs |
| Functional requirement ID | `create_todo`, `list_todos` | **YES** — generated by AnalysisAgent |
| Acceptance criterion ID | `ac_001`, `ac_002` | **YES (in acceptance_criteria only)** |
| Invented ID | `react_frontend_req` | **NO** — must not be invented |

## Changes Made

### 1. `backend/agents/planning/prompts.py` — Execution Prompt Rewrite

`build_planning_execution_prompt` now dynamically generates:
- An explicit **TECHNOLOGY STACK** block naming all tech names from the analysis artifact with `FORBIDDEN` label.
- A **VALID REQUIREMENT IDs** block listing exact functional requirement IDs copied from `AnalysisArtifact.result.functional_requirements` at runtime.
- A **VALID ACCEPTANCE CRITERIA IDs** block listing exact acceptance criteria IDs from `AnalysisArtifact.result.acceptance_criteria` at runtime.
- An **IDENTIFIER FORMAT RULE** block explaining the regex with valid snake_case examples.
- **CRITICAL EMPTY LIST RULE**: Explicitly instructs the model to leave `requirement_ids` as an empty list `[]` for infrastructure, architecture, or cross-cutting concerns (e.g., "setup database", "responsive UI framework") instead of inventing synthetic IDs.

### 2. `backend/agents/planning/agent.py` — Semantic Validator

Added `_make_execution_validator(analysis_artifact)` which produces a validator closure that:

1. **Semantic pre-check (raw dict)**: Runs BEFORE Pydantic validation to detect technology names or non-existent IDs in `requirement_ids` and `acceptance_criteria`.
2. **Produces a focused repair message** naming: the invalid values, why they are wrong (TECHNOLOGY NAME vs. invented ID), and the exact valid IDs to use.
3. **Does NOT sanitize**: Always raises `ValueError` — invalid data is always rejected.
4. **Pydantic still runs**: Structural validation runs after the semantic check passes.

The Execution section call in `_generate_and_validate` was updated to use `_make_execution_validator(request.analysis_artifact)` instead of the bare Pydantic lambda.

## Token Limit Truncation Fix

During runtime testing of the Execution section, the Qwen2.5-Coder model generated large structured JSON payloads that exceeded the default 4096 `max_output_tokens`, causing `JSONDecodeError` ("Unterminated string") during parsing.

- **Fix**: Increased `max_output_tokens` in `backend/llm/models.py` from 4096 to 8192 to safely support the monolithic `PlanningArtifact` breakdown generation.
